# 폴더 업로드 — 1단계 설계 (웹 일반 업로드)

작성일: 2026-06-15
상태: 설계 확정, 구현 전

## 개요

share-anything에 **폴더 업로드**를 추가한다. 디렉터리 구조(상대경로)를 보존해, 수신자가 폴더 트리로 보고 구조 그대로 ZIP으로 받을 수 있게 한다. 1단계는 **웹 "일반"(서버 경유, presigned multipart) 업로드 경로**와 그 수신 화면만 다룬다. 이후 단계가 재사용할 **공유 토대**(상대경로 데이터 모델, 수신 트리 뷰, 구조 보존 ZIP)를 여기서 만든다.

이 기능은 두 레포에 걸친다: `share-anything-web`(선택 UI·트리·ZIP)와 `share-anything`(백엔드 데이터 모델·업로드 엔드포인트).

## 목표

- 사용자가 웹에서 중첩 하위폴더를 포함한 **폴더를 업로드**할 수 있고 상대경로가 보존된다.
- 수신자가 폴더를 **트리로 보고**, 전체를 **구조 보존 ZIP**으로 받거나 개별 파일을 받을 수 있다.
- **완전한 하위호환**: 기존 평면 다중 파일 업로드는 동작이 바뀌지 않는다.

## 비목표 (1단계 제외)

- 보안(P2P) 폴더 전송 → 2단계.
- CLI 폴더 업로드 및 디스크에 실제 폴더 트리 복원 → 3단계.
- 개별 파일 다운로드는 폴더를 복원하지 않는다(해당 파일만 평면으로 저장).

## 전체 로드맵 (맥락)

1. **(본 문서) 웹 일반 업로드**: 토대 + 선택 + 트리 + ZIP.
2. **웹 보안(P2P)**: 1단계 토대·UI 재사용. P2P 메타데이터에 상대경로 추가.
3. **CLI**: 재귀 업로드 + 수신 시 디스크에 실제 폴더 트리 복원.

## 핵심 제약

브라우저는 보안상 사용자 디스크에 폴더 트리를 직접 만들 수 없다. 따라서 **웹 수신자는 구조 보존 ZIP(또는 개별 파일)**으로 받는다. 실제 폴더 트리 복원은 CLI(3단계)에서만 가능하다.

## 데이터 모델

- `file_share`에 nullable `relative_path` 컬럼 추가 (DB 마이그레이션 1건).
  - 값 = 업로드한 폴더 기준 POSIX 상대경로. 예: `src/index.ts`.
  - 빈 문자열/NULL = 루트 레벨 파일 → 기존 평면 동작. **하위호환.**
  - `file_name`과 **별도로** 저장한다(`file_name`은 계속 leaf 이름만). `file_name`을 쓰는 기존 표시·sanitization을 깨지 않기 위함.
  - 경로 sanitization: `..`·절대경로 거부, 구분자 `/`로 정규화, 선행 `/` 제거.

## 송신 플로우 (웹)

1. **선택** (`UploadPage.tsx` + `UnifiedFileBox/IdleUpload.tsx`의 드롭존):
   - 드롭존에 **폴더 드래그**: react-dropzone의 DataTransferItem/`getFilesFromEvent`로 디렉터리 엔트리를 재귀 순회해 파일 수집.
   - **"폴더 선택" 버튼**: `<input type="file" webkitdirectory>`.
   - **혼합 허용**: 느슨한 파일(루트, `relative_path=""`) + 폴더를 한 업로드에 섞을 수 있다.
   - 각 File은 상대경로를 갖는다(버튼은 `webkitRelativePath`, 드래그는 순회로 구성한 경로).
2. **미리보기**: 업로드 전 선택 결과를 **접기/펼치기 트리**로 표시(총 개수·크기). 수신 트리와 동일한 표현.
3. **전송**: 기존 `useMultipartUpload`(파일별 presigned multipart) 그대로. multipart-init 요청에 파일별 `relative_path`를 함께 전송.

## 백엔드 (업로드)

- multipart init / `file_share` 생성 경로가 파일별 `relative_path`를 받아 저장한다(1단계 = 웹/file 엔드포인트). 서버 측에서도 경로 sanitization.
- 응답·조회 DTO(`FileInfo`/`FileDetail` 등)에 `relative_path` 포함(수신 트리 구성용).

## 수신 플로우 (웹 풀페이지 — `DownloadFilePage.tsx`)

1. 파일을 `relative_path` 기준으로 **트리**로 묶어 표시(폴더 접기/펼치기). 모든 파일이 루트면 = 기존 평면 목록과 동일.
2. **개별 다운로드**: presigned URL로 R2에서 직통(해당 파일만).
3. **"전체 ZIP 다운로드"** → 구조 보존 ZIP:
   - 기본: **클라이언트 스트리밍 zip**. `client-zip`이 파일별 fetch 스트림(presigned R2 URL)으로부터 ZIP ReadableStream 생성 → File System Access API(`showSaveFilePicker` → WritableStream)로 디스크에 스트리밍. **메모리 일정, 서버 비용 0, 대용량 폴더 OK.**
   - 폴백: File System Access 미지원(Safari/Firefox 일부) 또는 소형 폴더 → **jszip 인메모리** → Blob 다운로드.
   - ZIP 엔트리 경로 = `relative_path`(풀면 트리 복원).

서버 비용 0의 근거: 파일 바이트는 항상 R2 → 브라우저 직통(presigned). 서버는 zip 생성에 관여하지 않는다.

## 에러 처리

- 경로 sanitization 실패 → 해당 파일 거부(클라이언트 + 서버 양쪽).
- 업로드 부분 실패 → 기존 multipart 재시도 동작 사용. 트리에 파일별 상태 표시.
- ZIP 스트리밍 중 특정 파일 fetch 실패 → 에러 표면화 + 재시도, 개별 다운로드로 폴백.
- 폴더 간 동일 파일명 = 경로가 다르므로 정상. 동일 경로 중복 = 마지막 우선/중복 제거.

## 하위호환

- `relative_path`가 NULL/빈값이면 현재 평면 동작과 **완전히 동일**. 기존 공유·CLI 업로드·수신자에 영향 없음.
- 모든 파일이 루트인 수신 트리 = 기존 평면 목록.

## 테스트

- 단위: 경로 sanitization(`..`·절대경로·구분자), 평면 경로 목록 → 트리 빌드, ZIP 엔트리 경로 구성.
- 통합: 중첩 폴더 업로드 → 수신 트리 정확 → "전체 ZIP"이 올바른 구조로 풀림 / 개별 다운로드 동작.
- 하위호환: 평면 다중 파일 업로드가 여전히 평면.
- 브라우저 매트릭스: 스트리밍 경로(크로미엄) + jszip 폴백(Safari/Firefox).

## 구현 시 정할 세부 (의도적 보류)

- jszip 폴백을 쓸 크기 임계값(스트리밍 미지원 브라우저에서 대형 폴더 경고 여부) — 구현 중 튜닝.
- 폴더 총 크기/파일 수 상한 — 기존 업로드 제한 정책을 따른다.
